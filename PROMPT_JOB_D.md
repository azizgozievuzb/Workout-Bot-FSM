## Промпт для CC

и сверка). Схему смотри в живой БД через `my-supabase`. Ниже — задание целиком.

### Жёсткие рамки (задел — СТОП и вопрос юзеру)

1. Удалять файлы можно ТОЛЬКО в бакете `workout-clips`. Бакеты `promises` и `avatars`
   не трогать ни при каких условиях (по ним — только чтение списков).
2. Чистка — ТОЛЬКО через Storage API (`storage.from_().remove()`). SQL `DELETE` по
   `storage.objects` ЗАПРЕЩЁН: строки исчезнут, а физические файлы останутся висеть в
   S3 — вес не уйдёт, целостность стораджа сломается. Read-only `SELECT` по
   `storage.objects` — можно и нужно (BEFORE-снимки, подтверждения).
3. Строки `workout_sessions` / `workout_exercises` НЕ удалять — это история XP/капель
   (инвариант №3 антифарм косвенно). Удаляются только файлы.
4. `pg_dump` (шаг 0) не взлетел → СТОП, вопрос юзеру. Без дампа дальше не идти.

### Шаг 0 — pg_dump перед патчем (заодно закрывает п.3 чек-листа даунгрейда)

1. `brew install libpq`; в PATH — `/opt/homebrew/opt/libpq/bin` (Intel:
   `/usr/local/opt/libpq/bin`); `pg_dump --version`.
2. Connection string: Dashboard → Connect → **Session pooler** (порт 5432; прямой
   `db.<ref>.supabase.co` может быть IPv6-only). Если пароля БД нет под рукой — СТОП,
   спроси юзера (reset пароля в дашборде API-ключи бэкенда не рвёт, но решает юзер).
3. `pg_dump -Fc -f workout_bot_$(date +%F).dump "<conn_string>"`, затем санити:
   `pg_restore --list <файл>` перечисляет таблицы (глазами увидеть `partnerships`,
   `workout_sessions`). Дамп — ВНЕ репо или путь в `.gitignore` (личные данные пары),
   не коммитить.

### Шаг 1 — разведка (read-only, до кода)

Через `my-supabase` SELECT-ами по `storage.objects` снять BEFORE:
- по трём бакетам: `count(*)`, `sum((metadata->>'size')::bigint)`;
- по `workout-clips` — разбивка старше/моложе 7 дней (по `created_at`);
- глазами проверить фактические пути: ожидается `{player_id}/{session_id}/{idx}.webm`
  (`workout.py:226`); если есть файлы вне схемы — удалять по возрасту файла, не по
  догадке о схеме; структура радикально другая → СТОП, вопрос.

Числа BEFORE записать — они же ожидание для смоука п.2.

### Шаг 2 — джоба `backend/schedulers/clips_lifecycle.py`

`purge_old_workout_clips()` по образцу `purge_fulfilled_promise_videos`
(`shelf_lifecycle.py`), но storage-driven:

- Константы в файле: `BUCKET = "workout-clips"` (никакой параметризации имени бакета —
  функция физически не может тронуть другой бакет), `RETENTION_DAYS = 7`.
- Обход: `storage.list()` НЕ рекурсивен — обходить два уровня «папок»
  (корень → `player_id` → `session_id` → файлы) с пагинацией (limit/offset, на
  дефолтные 100 не полагаться).
- Возраст — по `created_at` из метаданных листинга, НЕ по строкам БД. Причина:
  `purge_old_workout_data` (Job F) уже удаляет строки умерших пар, их файлы-сироты
  обязаны чиститься тоже.
- Удаление батчами ≤100 путей за `remove()`. Ошибка батча → лог + продолжить
  (не падать целиком — доедет следующей ночью, паттерн ретеншна обещаний).
- Финальный лог прогона (решение (д), кормит чек-лист даунгрейда): удалено N файлов /
  X МБ, осталось M файлов / Y МБ (сумма `size` из метаданных).
- `video_url` в `workout_exercises` после удаления файла: обнулить или оставить — на
  твоё усмотрение, выбор зафиксируй в «Допущения CC» в SESSION_STATUS. Справка: ссылки
  там битые by design (`/object/public/…` на приватном бакете), их никто не читает.
- Регистрация рядом с `register_shelf_jobs`: `trigger="cron", hour=3, minute=40` (UTC),
  `id="purge_old_workout_clips"`, `replace_existing=True`.

### Шаг 3 — разовая чистка = первый ручной прогон той же джобы (решение (б))

`backend/scripts/run_clips_purge.py`: вызывает ту же функцию, печатает ВСЁ, что делает

логикой НЕ заводить. Прогон — по смоук-чеклисту ниже (ожидание — ДО прогона).

### Шаг 4 — сверка ретеншна обещаний (решение (а), строго read-only)

Список файлов бакета `promises` (Storage API) против `shelf_items`
(`video_path`, `report_video_path`, статусы). Ожидание: каждый файл привязан к живой
строке; строк `fulfilled` старше 30 дней с непустыми путями нет (джоба
`purge_fulfilled_promise_videos` живая). Расхождения — ОТЧЁТОМ юзеру списком; ничего
не чинить и не удалять (фикс — только отдельным решением юзера). `avatars` не трогать.
