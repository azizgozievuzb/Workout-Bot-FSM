### Сеть: холодный старт и round-trip

Фронт (Vercel, edge — быстро):

| Запрос | TTFB | Размер |
|---|---|---|
| `index.html` | 1.15 с (первый) | 587 Б |
| `index-*.js` | 0.63 с | 195 КБ (сжатый) |
| `index-*.css` | 0.84 с | 21 КБ |

Бэк (Railway). **Главное наблюдение — разложение по фазам:**

```
dns=0.003  tcp=1.100  tls=1.204  ttfb=1.306   ← первый запрос
dns=0.003  tcp=3.106  tls=3.216  ttfb=3.321   ← и такой бывает
```

DNS ≈ 3 мс. `tls − tcp` = 104 мс и `ttfb − tls` = 102 мс → **реальный RTT до Railway
≈ 100 мс, обработка `/health` ≈ 0**. А `tcp` = 1.1 / 3.1 / 4.1 с — это ровно 100 мс
плюс 1, 3 или 7 секунд: **классическая картина потери SYN-пакета** (ядро ждёт 1 с,
ретрансмитит, ждёт 2 с, ретрансмитит…). Сервер тут ни при чём.

Round-trip живых эндпоинтов, 5 запросов по одному соединению (первый — с ценой
соединения, дальше — чистая обработка):

| Эндпоинт | 1-й | Далее (устойчиво) | Похоже на |
|---|---|---|---|
| `/health` (без БД) | 1.32 с | **0.10 с** | 1 RTT, БД не трогается |
| `/users/me` | 3.60 с | **0.61–0.64 с** | ~1 запрос в Supabase |
| `/payments/tier-prices` | 3.85 с | **0.60–0.73 с** | ~1 запрос |
| `/notifications/unread-count` | 3.10 с | **0.86–0.92 с** | ~2 запроса |
| `/stats/partner` | 1.56 с | **0.85–0.99 с** | ~2 запроса |
| `/shelf/catalog` | 1.62 с | **1.37–1.45 с** | ~3 запроса |
| `/players/me/schedule` | — | 0.89 с | |
| `/stats/me` | — | 1.17 с | |

Из `/health` (0.10 с) и остальных видно: **каждый поход Railway → Supabase стоит
≈ 0.5 с и они складываются последовательно** — 1 запрос ≈ 0.6 с, 2 ≈ 0.9 с, 3 ≈ 1.4 с.

**Холодный старт Railway-бэка:** отдельного «сна» поймать не удалось — бэкенд не спит,
его будят собственные джобы (ежечасные) и вебхук. Разброс первого запроса
(1.3 / 2.3 / 3.1 / 4.3 / 5.5 с при повторных заходах) объясняется потерями SYN, а не
пробуждением: у «спящего» контейнера долгим был бы `ttfb` при быстром `tcp`, а картина
ровно обратная. Один выброс за замер: `/notifications/unread-count` = **69 с** — не
воспроизвёлся; отмечаю как факт, объяснения пока нет.

### Топ-3 подозреваемых (гипотезы, не выводы)

1. **Потери SYN на пути Ташкент → Railway: +1…+3 с на каждое НОВОЕ соединение.**
   Обоснование: `tcp` квантуется по 1/3/4 с, а `tls − tcp` и `ttfb − tls` стабильно
   ≈100 мс — потерян именно первый SYN, дальше всё быстро. Это самый крупный
   единичный штраф в замере, и он бьёт ровно по холодному старту, когда браузер
   открывает соединения впервые. Направление проверки: сколько соединений реально
   открывает мини-апп на старте (keep-alive / HTTP-2 переиспользование), нужен ли
   `Connection: keep-alive`-пинг, стоит ли регион Railway ближе к пользователям.
2. **~0.5 с на каждый запрос Railway → Supabase, складывающиеся последовательно.**
   Обоснование: `/health` 0.10 с против `/users/me` 0.62 с и `/shelf/catalog` 1.40 с —
   шаг ровно в полсекунды на запрос. Похоже на межрегиональную задержку (Railway и
   Supabase в разных регионах) плюс последовательные `await`-ы внутри хендлера. Именно
   это даёт «панель обновляется с заметной задержкой ПОСЛЕ действия» (дополнение S63):
   дешёвой причины в коде экранов действительно нет, цена сидит в round-trip.
   Направление проверки: регионы двух сервисов, параллелизация запросов внутри
   хендлеров, объединение в один RPC.
3. **Один JS-чанк 623 КБ (192 КБ gzip) без code splitting.**
   Обоснование: 0.63 с только на скачивание с Vercel на быстром канале; на мобильной
   сети это заметно дороже, и до его выполнения на экране ничего нет. Половина веса —
   `react-dom` + анимационный стек (`motion-dom`/`framer-motion`), который нужен не на
   первом кадре. Направление проверки: ленивый импорт тяжёлых экранов (тренировка,
   админ-куб), вынос анимаций из критического пути.

**Побочные находки (не входят в топ-3, но дешёвые):** `bg_dark.png` + `bg_light.png` =
949 КБ в `public/` не упоминаются в коде ни разу — мёртвый вес; фолбэк-лица
`woman_*.png` (1.04 МБ) грузятся только если у пользователя нет своего фото, то есть у
живого игрока не грузятся никогда, но лежат в сборке.
