### Модель (решения юзера, НЕ обсуждаются)

Вне grace: смена всегда платная (`schedule_change` из `app_shop_items`, сейчас 100💧),
вступает со следующего понедельника (pending), **30-дневный кулдаун удаляется целиком**.
Ограничитель частоты = цена + понедельничное вступление.

1. **(а)** Пока pending не вступил — его можно **отменить с полным возвратом уплаченного**.
   Возврат = прямое зачисление в `drops_balance` (зеркало `_charge_drops`), НЕ путь
   начислений за тренировки: XP не трогать, антифарм-кап и месячный кап возврат не видят.
2. **(б)** Пока pending не вступил — выбор дней можно **править бесплатно, без лимита**
   (правка заявки, не новая покупка). Применяется последний выбор.
3. **(в)** Grace 14 дней и первичная установка — **НЕ трогать** (ветки 1 и 2 в
   `set_schedule` остаются как есть).
4. **(г)** Наставник — **ничего нового**: видит только вступивший график, никаких
   уведомлений о заявке/правках/отмене. Экраны наставника не трогать.

### Скоуп

**Бэкенд — `backend/api/routers/schedule.py`:**
- Ветка 3 `set_schedule` (вне grace): убрать 409 `SCHEDULE_COOLDOWN` и всю
  кулдаун-математику. Новая развилка:
  - pending НЕТ → списать цену (`_charge_drops`), записать `pending_main_days` +
    `pending_schedule_from` (следующий пн, как сейчас) + запомнить уплаченную цену;
  - pending ЕСТЬ и `local_today < pending_schedule_from` → **бесплатная правка**:
    обновить только `pending_main_days`, ничего не списывать, дату вступления не двигать;
  - pending ЕСТЬ, но `local_today >= pending_schedule_from` (заявка уже должна
    примениться) → 409 `PENDING_ALREADY_DUE` — не править то, что применяет джоба.
- Новый эндпоинт отмены (например `POST /players/me/schedule/cancel-pending`):
  pending нет → 409 `NO_PENDING`; `local_today >= pending_schedule_from` → 409
  `PENDING_ALREADY_DUE`; иначе вернуть уплаченное на `drops_balance`, очистить
  `pending_main_days`, `pending_schedule_from` и колонку уплаченного. Read-then-write
  как в `_charge_drops`.
- `_build_resp`: `can_change_now` при заданных днях всегда `true`,
  `next_change_available_at` всегда `null` (поля оставить — фронт-совместимость).
  Отдать фронту уплаченную цену pending (для текста «вернём N 💧»).
- `schedule_changed_at` живёт как журнальная отметка (пишется при покупке), но НИКАКАЯ
  логика её больше не читает для гейта. `COOLDOWN_DAYS` удалить.
- Docstring модуля обновить под новые правила.

**Миграция (через `my-supabase`):** одна nullable-колонка в `users` — уплаченная за
текущий pending цена (имя на твоё усмотрение, например `pending_schedule_paid_drops`).
Ставится при покупке, очищается при отмене и при применении pending (найди место, где
джоба применяет pending → там же очистка). Возврат обязан равняться фактически
уплаченному, а не цене на момент отмены — цены в `app_shop_items` могут меняться.

### Дельта-смоук-чеклист (вести по §1-E: по одному пункту, ожидание ИЗ БД до действия, подтверждение SELECT-ом)

Живой кейс: у Cell `schedule_changed_at` ≈ 12.08 → по старой логике кулдаун до 11.09.
Цену смены на смоук можно снизить SQL-ом (BEFORE-снимок обязателен, все подмены
печатать, откат сверить 1:1).

0. BEFORE-снимок: `main_days`, `pending_main_days`, `pending_schedule_from`,
   `schedule_changed_at`, новая колонка, `drops_balance`.
1. **Кулдаун мёртв:** сразу после деплоя кнопка смены у Cell активна, хотя по старой
   логике кулдаун шёл бы до 11.09; в ответе API `can_change_now=true`,
   `next_change_available_at=null`.
2. **Платная смена:** покупка → баланс −цена, pending записан, дата вступления =
   ближайший пн, новая колонка = уплаченная цена; строка «📅 С понедельника …» на месте.
3. **Бесплатная правка:** изменить дни pending → `pending_main_days` обновились,
   баланс НЕ двинулся, дата вступления НЕ двинулась.
4. **Отмена:** отменить → баланс +уплаченное (ровно), pending-поля и колонка очищены,
   действуют старые дни.
5. **Вступление в пн:** купить заново → pending применился в понедельник (механизм
   проверен живьём 17.08 — здесь допустима SQL-подмена даты с печатью подмены):
   `main_days` = новые, pending и колонка очищены.
6. **Повторная смена сразу после вступления, без кулдауна:** тут же новая покупка →
   вторая оплата прошла, новый pending записан, никаких 409.
7. Негативные: отмена без pending → `NO_PENDING`; правка/отмена при
   `local_today >= pending_schedule_from` → `PENDING_ALREADY_DUE`; покупка при
   балансе < цены → `INSUFFICIENT_DROPS`, ничего не записано.
8. Откат: вернуть цену и подменённые даты, сверка с BEFORE 1:1 булевой таблицей.
