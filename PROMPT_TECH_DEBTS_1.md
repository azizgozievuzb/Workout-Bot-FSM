### Кусок 1 — онбординг врёт про смену фонового фото (BACKLOG 23.08 п.2, решение юзера)

Онбординг-селфи становится фоном приложения (`users.photo_url`) и не меняется никаким
платным путём (покупка «своё фото» меняет только карточку — `card_photo_url`). Текст
онбординга обещает «потом можно поменять за отдельную плату» — дезинформация.
1. Найди точный текст обещания (grep по онбординг-экранам/текстам).
2. Замени на утверждённое юзером: **«это фото станет вашим фоном, изменить его будет
   нельзя»** (формулировку встроить в стиль экрана, смысл не менять).
3. Перепроверь grep-ом: путей записи `users.photo_url` ПОСЛЕ онбординга действительно
   нет. Если найдётся живой путь записи — СТОП, доложи юзеру (тогда запись BACKLOG
   неверна и врать перестанет онбординг иначе).

### Кусок 2 — аудит порталов: тема не достаёт (BACKLOG S59 №4; уроки №2 и №17)

После фикса S64 (`10387f5`) тема приложения переопределяет `--tg-theme-*` в своём
поддереве и вешает класс темы на корень портала — но проверено это было точечно.
1. Найди ВСЕ `createPortal` проекта.
2. Для каждого: корень портала получает класс темы; всё внутри красится только
   переменными, которые реально доезжают (переопределённые `--tg-theme-*` или токены
   нашей темы); никаких голых цветов и нативных дефолтов.
3. Почини найденные дыры. Итог — таблица в SESSION_STATUS: портал → файл → статус
   (был ок / починен что именно).

### Кусок 3 — pressed/disabled/busy у кнопок глобально (BACKLOG S54 №5-№15, S59 №2)

Состояния добавлялись точечно по находкам смоуков — нужен системный проход.
1. Инвентаризация всех классов кнопок (grep по `button`/`.btn`/`cube-btn` и родне).
2. У каждого класса: видимый pressed (`:active`) и видимый `:disabled` (блёклость +
   курсор — паттерн `.cube-btn-sm:disabled` из 8d.1).
3. Кнопки, стреляющие запросами: busy-состояние на время запроса (disabled + понятный
   лейбл/спиннер). Где double-submit guard уже есть (8c.1) — не дублировать, только
   довесить видимость (урок №3: состояние есть в логике — покажи глазу).
4. Без редизайна: только состояния существующих кнопок. Итог — список классов и что
   добавлено, в SESSION_STATUS.

### Кусок 4 — перф-замер, БЕЗ фиксов (BACKLOG S62 №4 + дополнение S63)

Юзер жалуется на медленный старт и задержку панелей после действий. Правило проекта:
сначала мерить (урок №10). Сними базовую линию:
1. Бандл: продовая сборка, размер по чанкам (топ-10 тяжёлого, суммарный вес).
2. Холодный старт: цепочка запросов мини-аппа с прод-URL (что грузится, что
   последовательно, где цепочки auth → данные), тайминги.
3. Round-trip 3–4 живых действий (экран графика, витрина, открытие R-панели) — по
   серверным логам Railway / curl-замерам эндпоинтов.
4. Холодный старт Railway-бэка: время первого ответа после простоя vs повторного.
Итог — компактный блок цифр в SESSION_STATUS: методика (чем мерил), топ-5 тяжёлого,
топ-3 подозреваемых с обоснованием. Оптимизации НЕ делать — это вход для будущей
постановки перф-патча.
